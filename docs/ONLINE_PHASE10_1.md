# コタロの大格闘 Online — Online Phase 10.1 調査報告（HIT 反映の体感遅延）

実機 2 端末で「攻撃が見た目上当たってから HIT / GUARD が出るまで少し待たされる」と感じた件について、どこで何 ms かかっているかを計測し、
不要な待ちだけを 1 か所削った。HOST authoritative（命中・ガード・ダメージ・吹っ飛びは HOST が決める）・予測・70ms 補間・遅延補償（上限 200ms）・
泡（遅延補償なし）・ガード（遅延補償なし）・試合の流れは変更していない。

## 1. 計測の方法
- 2 ページ（HOST / GUEST）を人工遅延の順序保証チャネルでつなぎ（Ping も流して時計のずれを推定）、同じマシンの `Date.now()` で両方の画面の出来事を比べた。
- ゲームのコードは変えず、テスト用のページ側で関数を包んで時刻だけを記録：押下・技の開始・判定が出たフレーム・**画面上の接触**（その画面に見えている攻撃判定 × 見えている体）・
  HOST の判定（`receiveHit` / `receiveGuard`）・命中イベント `mh` の送信 / 受信・HOST の入力の受信 / 適用・その後の最初の描画・被弾 / ガード硬直の見た目。
- 2 人とも地上で静止し、攻撃側が相手の方を向いた状態から 1 回ずつ攻撃（各 4 回の中央値）。片道 15ms 設定（実測の片道 約 25ms）と 50ms 設定（実測 約 58ms）。

## 2. HIT が画面に出るまでの経路
| | HOST が攻撃（コタロ → ルミポ） | GUEST が攻撃（ルミポ → コタロ） |
|---|---|---|
| 攻撃側の画面の技 | HOST の本当の状態（押した次のステップから） | GUEST の予測（押した次のステップから） |
| 攻撃側の画面の相手 | ルミポは HOST の本当の位置 | コタロは 70ms 補間（HOST の過去） |
| 判定 | HOST の同じステップ（Combat.resolve） | 入力が HOST に届き（片道）、HOST の入力キューから適用 → 同じ startup の後に HOST で判定（遅延補償で GUEST の見ていたコタロの位置） |
| 攻撃側の画面の反応 | 同じステップ → 次の描画（**0〜4ms**） | `mh` が届いた瞬間に火花・音・白く光る（判定 + 片道 + 描画）。コタロの被弾の姿勢・吹っ飛びは 70ms 補間で後から |
| 相手側の画面の反応 | GUEST：`mh` で火花・音・白く光る。ルミポの被弾の姿勢・ヒットストップ・吹っ飛びは HOST の状態 `st` で（予測を置き換える） | HOST：同じステップ → 次の描画（0〜3ms） |

## 3. 計測結果（変更前・押下からの ms・中央値）
### HOST → GUEST（片道 約 25ms）
| 技 | HOST：判定 | HOST 画面の反応 | GUEST：火花（mh） | GUEST：ルミポの被弾の姿勢 | GUEST 画面でコタロの技が見た目上触れる |
|---|---|---|---|---|---|
| ぽよん | 56 | 60 | 91 | 104 | 154 |
| クラゲ電撃 | 156 | 158 | 190 | 203 | 252 |
| 泡 | 655 | 658 | 689 | 706 | （泡は触れる前に弾ける） |
| ぽよん（GUEST ガード） | 53 | 55 | 88 | 89 | 139 |

→ HOST 画面は判定と同時。GUEST 画面では **反応がコタロの技が見た目上触れるより約 60ms 先に出る**（コタロは 70ms 補間で遅れて見えるため）。遅れではない。

### GUEST → HOST（片道 約 25ms）
| 技 | GUEST 画面の接触 | HOST 受信 → 適用 | HOST 判定 | HOST 画面の反応 | GUEST：火花（mh） | GUEST：コタロの被弾の姿勢 | 接触 → 火花 | 接触 → 姿勢 |
|---|---|---|---|---|---|---|---|---|
| ぽよん | 55 | 30 → 38 | 88 | 90 | 123 | 189 | **68** | 134 |
| クラゲ電撃 | 159 | 33 → 41 | 192 | 194 | 225 | 285 | **67** | 133 |
| 泡 | 639 | 34 → 38 | 688 | 691 | 724 | 789 | **84** | 150 |
| ぽよん（HOST ガード） | 52 | 27 → 39 | 89 | 90 | 123 | 190 | **67** | 134 |

### 片道 約 58ms
- HOST → GUEST：HOST 画面は 1〜2ms。GUEST の火花は判定 + 67ms、ルミポの被弾の姿勢は判定 + 84ms。
- GUEST → HOST：接触 → 火花 133〜167ms、接触 → コタロの被弾の姿勢 199〜216ms。

### 内訳（GUEST の攻撃・接触 → 火花 68ms の例）
| 部分 | ms | 必要か |
|---|---|---|
| 入力が HOST へ（片道） | 約 25 | ネットワーク（必要） |
| HOST の入力キューで次のステップまで待つ | 中央値 約 9（全入力の分布：中央値 9 / 平均 11〜15 / 90% 点 24〜27。10% 弱は 2 フレーム以上） | 60Hz の位相差の平均 8.3ms は避けられない。残りは揺れを吸収するための入力キュー（Phase 3 / 4 の設計） |
| HOST で startup → 判定 | GUEST と同じフレーム数（差は 0） | — |
| 命中イベントが GUEST へ（片道） | 約 25 | ネットワーク（必要） |
| 受信 → 描画 | 約 6 | 描画 1 フレーム（必要） |
| （姿勢・吹っ飛びまで）70ms 補間 | 約 66 | コタロの表示は 70ms 補間（ジッタを滑らかにするため。変更しない） |

- 処理負荷：オンライン中の 1 ステップ 0.2ms（99% 点 1.3ms）、1 描画 0.4ms（99% 点 1.9ms）。HOST・GUEST とも遅延の原因ではない（PC。スマホは未計測）。

## 4. 結論
- **HOST の画面では、どちらの攻撃でも HIT / GUARD は判定と同じステップで表示される（0〜4ms）**。ネットワークの待ちは無い。
- 体感の遅れが実際に生じるのは「GUEST が攻撃した時の GUEST の画面」：接触 → 火花 = **往復（RTT）＋ HOST の入力キュー（中央値 約 9ms）＋ 描画 1 フレーム**。
  コタロが吹っ飛び始めるのはさらに **70ms 補間の分** 後。HOST authoritative を保つ限り、往復分は必要な遅れ。
- HOST が攻撃した時の GUEST の画面は逆に「コタロの技が触れて見える前に被弾が出る」（約 60ms 先）。
- 泡（GUEST の攻撃）は近接より約 16ms 多い（泡の移動が 1 ステップ 9 の飛び飛びで、HOST で泡が出るのが片道ぶん遅い分）。Phase 7 の既知事項（GUEST の自分の泡は「今」、
  コタロは 70ms 前で表示）は、コタロが動いている時に「見た目で重なった時刻」と「HOST で当たった時刻」をずらす（近づく時は早く・離れる時は遅く / MISS）。静止の計測では差は出ない。
  HOST の泡は GUEST の画面でコタロと同じ 70ms 前の時刻で表示し、命中の消滅イベントで即座に弾けるので、ルミポに届く少し手前（約 38 = 70ms × 540）で弾けて見える。
- 泡の消滅イベントの受信検証で発射した側・攻撃 ID が落ちている件（Phase 10 で発見）は、命中の時刻には関係しない（命中の表示は `mh`。泡はその前の状態で引き継ぎ済み）。今回は変更していない。
- ガードも同じ経路（GUARD は HIT と同じ `mh` の列）。ガードの成立は HOST の今の状態のまま。体感はガードの姿勢が予測で即座に出るため HIT より分かりやすいが、結果の到着時刻は HIT と同じ。

## 5. 不要な待ち（1 か所）と変更
**GUEST の自分（ルミポ）の被弾 / ガードの姿勢・ヒットストップ・吹っ飛びが、命中イベントの後「次の 30Hz の状態」まで待っていた**（命中イベントには姿勢・吹っ飛びの値が無く、
状態は 2 ステップに 1 回のため、HOST は分かっているのに最大 1 ステップ遅れて届いていた）。

変更：HOST は命中・ガードがあったステップだけ、30Hz の順番を待たずにそのステップの状態をすぐ送る（`online-move.js` の `afterHostStep`）。
送る内容・判定・数値・送る頻度（命中の時だけ 1 件増える）以外は同じ。

| 変更前 → 変更後（中央値） | 片道 約 25ms | 片道 約 58ms |
|---|---|---|
| GUEST：火花 → ルミポの被弾の姿勢 | 17 → **0** | 18 → **0** |
| GUEST：HOST の判定 → ルミポの被弾の姿勢 | 51 → 35 | 84 → 68 |
| GUEST：火花 → コタロの被弾の姿勢（補間） | 66 → 50〜66（命中のステップの状態が届くので補間の切り替えも正確に） | 66 → 53〜66 |
| HOST 画面 判定 → 反応 | 1〜4 → 1〜3（変化なし） | 1〜2 → 1〜3 |

GUEST の攻撃の接触 → 火花はこの変更では変わらない（往復 + 入力キューで決まる）。片道 58ms の比較で見える 162 → 134 などの違いは入力キューの待ちの揺れ（7〜37ms）による。

### 診断の追加（実機の確認用・ゲームには影響なし）
- GUEST の診断「時間」の表に **「見た目の接触→HIT」**（自分の画面で技がコタロに触れて見えてから HIT が届くまで。中央値と最大）。テストの計測値と一致することを確認。
- 診断の 1 行目に **fps**（実機で描画が遅れていないかの目安）。

## 6. 変更しなかったこと（理由）
- HOST の入力キュー（未適用 3 件超で追いつき / 2 件以上が 0.5 秒続いたら追いつき）：平均の余分は 3〜6ms で、まれに 17〜33ms。小さくすると入力が間に合わない回数（予測とのずれ）が増える。
  実回線での分布を見てから判断する（診断の「未適用」「追いつき」「続けた」）。
- 70ms 補間・遅延補償・泡 / ガードの遅延補償なし：今回の遅れの主な原因ではない、または変更が禁止されている。
- 仮の命中フィードバック（自分の画面で触れた瞬間の仮の演出）：実回線の「見た目 HIT → HOST MISS」の割合（診断の HIT→MISS）を確認してから検討する。
  ガードは遅延補償が無いので「仮に当たった → 実際は GUARD」も起こる。今回は実装しない。
- 命中の時にコタロの被弾の姿勢を補間より先に出す：位置（70ms 前）と姿勢がずれて見えるため行わない（白く光る・火花・音はすでに命中イベントの到着で即座に出ている）。

## 7. 副作用の確認
- 各計測（HOST / GUEST × ぽよん・電撃・泡・ガード）：両画面のダメージ・吹っ飛びの値が一致、命中イベントは 1 回ずつ、重複 0、HIT+GUARD 0、ガードは GUARD のまま。
- 予測の snap：計測スクリプトでは変更前後とも 8（試行ごとにルミポを瞬間移動させているため。変更前のコードで同じスクリプトを実行して同数を確認）。通常の対戦（Phase 10 テスト）では 0。
- Phase 10 テスト（READY・カウントダウン・KO・リスポーン・勝敗・再戦・古い試合のパケット・3 試合以上・予測）**26/26**、Phase 9 テスト（KO・無敵・ダメージ一致・KO の重複・終了後の命中・DRAW）**26/26**。

## 8. 実回線で次に確認すること
1. GUEST の診断「見た目の接触→HIT」（ぽよん・電撃）と PING。往復 + 10〜20ms 程度なら設計どおり。大きく上回るなら HOST の入力キュー（「未適用」「追いつき」）を確認。
2. HOST 側で遅れを感じる場面が「GUEST の攻撃がコタロに当たった時」か「コタロの攻撃」か。HOST の画面の反応は判定と同時なので、HOST で遅れを感じる場合は
   (a) 遅延補償で「離れた後に当たった」（HOST の診断「補償だけHIT(>60)」）、(b) 描画の遅れ（診断の fps）、(c) Version 1.0 のヒットストップ（ぽよん 5F・電撃 7F）の見え方、を切り分ける。
   CPU 対戦で同じ技を当てた時と比べるのが早い。
3. GUEST の診断「見た目×HOST」の HIT→MISS の割合（仮フィードバックを検討する場合の判断材料）。
4. スマホでの fps（60 未満が続くと描画 1 フレームの遅れが増える）。
