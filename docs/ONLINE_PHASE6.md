# コタロの大格闘 Online — Online Phase 6 完成報告

「クラゲ電撃のオンライン同期実験」。ぽよんアタックに加えて、コタロの既存必殺技「クラゲ電撃」1 種類だけをネット越しで使えるようにしました。
HOST authoritative のまま（技を出せるか・命中・ダメージ・吹っ飛び・ヒットストップを決めるのは HOST だけ）。
Phase 5 の Lag Compensation は **ON・上限 200ms を通常状態**のまま維持し、OFF は診断・比較用に残しています。
バブルショット・ガード・KO・ストック・勝敗・ルミポの性能調整・rollback・ゲーム世界の巻き戻しは行っていません。

## 1. 使ったクラゲ電撃（Version 1.0 のコードをそのまま使用。値は一切変更なし）
`src/moves.js` の `KG.MOVES.jellyShock` と `src/fighter.js` の既存処理をそのまま使っています。

| 項目 | v1.0 のコードの値 |

| startup | 1〜9F（判定なし。溜めの演出 `shockCharge`・溜め音 `shockCharge`） |
| active | 10〜14F（5F）。攻撃判定は 2 つの矩形（横の帯 250×92・縦の帯 176×170）。10F に放電の演出 `shockBurst`・放電音 `shockZap` |

キャラクターは Phase 5 と同じ（HOST = コタロ、GUEST = ルミポ）。操作実験の間だけ、両者の「必殺」を既存のクラゲ電撃にしています
（技選択 `selectMove` をこのインスタンスだけ差し替え。終了時に削除。技データ・Fighter・CPU は変更なし）。ルミポの正式な技構成を決めるものではありません。

## 2. 必殺の入力の送り方（GUEST → HOST）
- Phase 4 の `ap`（攻撃を押した回数の累計）と同じ考え方で、入力メッセージ `mi` に **`sp` = 必殺を押した回数の累計** を追加しました。
- HOST は `sp` が前の値より増えた入力だけを「必殺を押した瞬間」として既存の `cmd.pressed.special` に変換します。押しっぱなしでは増えないので、毎フレーム発動しません（テスト：K を 1.8 秒押し続けても 1 回）。回数が減る・整数でない値はメッセージごと破棄。
- GUEST から送るのは「押した」だけ。HIT・ダメージ・吹っ飛び・座標は送りません（偽の `mh` / `ma` を GUEST から送っても HOST は受け付けない＝テスト済み）。
- 遅延補償の時間参照 `rs`（HOST 状態番号）/ `rf`（補間の割合）は、攻撃 **または** 必殺を押した入力に付けます（同じ入力で両方押した時は 1 回だけ計算）。
- 通信形式の番号 `PROTO_VERSION` は 6（Phase 5 以前とは接続しません）。

## 3. Attack ID
- **攻撃 ID = 押した入力の番号 × 2 + 技の種類**（0 = ぽよんアタック / 1 = クラゲ電撃）。HOST のコタロの技も「通し番号 × 2 + 種類」。
- 同じ入力で J と K を同時に押しても ID が重ならず、ID だけで技の種類が分かります（命中イベント `mh` と結果 `ma` は形式を変えずにそのまま使えました）。
- HOST と GUEST の予測で同じ規則（`aidFor()`：その技の元になった最後の押下の番号）で付けるので、予測した技と HOST の技を ID で照合できます。
- 同じ ID は 1 回だけ：受理の確認・結果（`ma`）・命中イベント（命中番号の集合で 1 回だけ）・効果音・演出の表示はすべて ID / 命中番号ごとに 1 回。古い命中番号（64 件以上前）は捨てます。

## 4. GUEST 側の予測（Prediction）
- K を押した次のローカルステップで、予測用ルミポ（Phase 3 と同じ Fighter クラス）の既存処理がそのままクラゲ電撃を開始します。出せるかどうかの判断も既存の Fighter（再使用待ち・技中・被弾中・先行入力 0.1 秒）。
- 再使用待ちも予測に含めるため、HOST 状態に「クラゲ電撃の再使用待ちが始まってからのステップ数」を載せ、GUEST は既存処理と同じ引き算を同じ回数繰り返して **全く同じ値** を作ります（小数の丸め誤差で 1 フレームずれない）。
  あわせて「必殺の先行入力の残り」「最後の必殺押下の番号」も載せています。
- 予測では命中を一切判定しません（HIT・ダメージ・吹っ飛びは HOST から届いた時だけ）。
- 測定：**K を押してから予測で技が始まるまで 平均 6〜7ms（最大 16〜29ms）**＝次のフレーム。スマホの「必殺」ボタンでも 3〜7ms。

## 5. HOST での発動判定・攻撃拒否
- HOST は届いた入力を Phase 3 の入力キューで 1 ステップ 1 件ずつ既存の `Fighter.update()` に渡すだけ。被弾硬直中・別の技の途中・再使用待ち中・ヒットストップ中などは既存の規則どおり出ません。
- 押下から 14 ステップ（先行入力 0.1 秒 ＋ ヒットストップ 7F ＋ 余裕）以内に始まらなかった押下は「拒否」として技ごとに数えます（診断）。
- GUEST の予測だけで出ていた技（HOST では出なかった）：
  - 作り直し（reconciliation）で予測から消えたら、**クラゲ電撃がまだ溜め（9F 以前）なら溜めの終わりまでで止め、放電の演出・放電音は出しません**。被弾中ならすぐに消します（被弾の表示を優先）。
  - ぽよんは Phase 4 と同じく見た目だけ最後まで再生。
  - どちらも当たり判定は持ちません（GUEST は命中を判定しない）。HOST で出ていない技で HIT が起きることはありません。
- テスト（ping 30・60・100ms・揺れあり）：HOST の電撃が当たる前後に GUEST が K → HOST は拒否、GUEST の画面に放電・放電音は 0 回、ダメージは両画面で一致（ping 200ms の例外は 14 章）。

## 6. startup / active / recovery と再使用待ちの同期
- HOST 状態（30Hz）でルミポの「技のフレーム」「攻撃 ID（=技の種類）」「先行入力」「再使用待ち」を送り、GUEST は予測を HOST の値に合わせてから未確認の入力を適用し直します（Phase 3 と同じ）。
  startup・active・recovery は別々に送らず、既存の「技のフレーム」1 つで決まります。
- コタロの技は状態のフラグに「クラゲ電撃か」の 1 ビットを足し、GUEST はフレームと種類から既存の描画（伸縮・発光）で表示します。
- GUEST の画面の HUD の必殺ゲージ（コタロ）は、表示中の技が終わった時から 0.7 秒の見た目だけの再使用待ちにしています（判定には使わない）。
- 予測と HOST の開始フレームが合っているか：連続入力テスト（下の 11 章）で、ぽよん 3 回・クラゲ電撃 2 回・拒否（ぽよん 1・電撃 1）が HOST と GUEST の予測で完全に一致。人工遅延テストでも GUEST が予測した電撃のうち HOST で出なかったのは各 1〜4 回 / 約 150 回（主に「HOST では既に被弾していた」時）。

## 7. Lag Compensation への統合（Phase 5 の仕組みを最小限で一般化）
コピーして 2 つ目の仕組みを作るのではなく、Phase 5 の処理の **対象の決め方だけ** を変えました。
- 対象：**GUEST の近接攻撃 = 体の攻撃判定を持ち、飛び道具を出さない技**（`isLagCompMove`：ぽよんアタック・クラゲ電撃が該当。泡のような飛び道具は対象外）。技の名前では分けていません。
- 巻き戻し量は「押下を HOST が適用した瞬間」に 1 回だけ決め（Phase 5 と同じ検証：HOST が送った番号か・未来でないか・上限 200ms）、**その押下から始まった技の action に付けます**（`a.lag`）。技の種類が違っても同じ規則。
- 判定：既存の `Combat.resolve()` のまま。コタロの `getHurtboxes()` だけが「ルミポの技が補償の対象・巻き戻し量あり・**今その技の攻撃判定が出ている**」時に、HOST の履歴から作った過去の Hurtbox を返します。
  クラゲ電撃の 2 つの矩形・5F の判定もそのまま既存処理が使います（Hitbox の形や判定フレームを Lag Compensation 側で持たない）。
- 1 回の電撃で同じ相手に 1 回だけ当たるのは既存の `hitVictims` のまま（テスト：5F × 2 矩形でも命中 1 回）。
- 安全のための制限（Phase 5 と同じ）：参照する過去から今までに「被弾」「場外・復帰」「瞬間移動」があれば巻き戻さない。ゲーム世界（コタロの本当の位置）は巻き戻さず、ダメージ・吹っ飛び・ヒットストップは今の状態に既存処理で適用。HOST の攻撃（コタロ → ルミポ）は補償なし。

## 8. startup を含む巻き戻しの基準（採用した基準と理由）
**採用：「GUEST の画面で、電撃の判定が出た瞬間に見えていたコタロ」を基準にする。**
実装上は「押下を適用した時に決めた巻き戻し量（今 − 押した瞬間に GUEST が見ていた HOST 時刻）を、判定が出ている各フレームでそのまま使う」＝参照するステップは `今 − 巻き戻し量`。

理由：
- GUEST の画面では、K を押した後も startup の 9F の間コタロは補間表示で同じ速さで進み続け、電撃（放電の演出と判定）は押してから 9F 後に出ます。
  プレイヤーが「当たった / 外れた」と感じるのは **放電が出た瞬間のコタロの位置**であって、押した瞬間の位置ではありません。
- 押した瞬間の位置に固定すると、startup の 150ms の間に動いたコタロを「止まっていた」ものとして判定してしまい、かえって見た目とずれます。
- 一定の巻き戻し量で「今 − 巻き戻し量」を見れば、HOST で判定が出る 10〜14F の各フレームが、GUEST の画面の 10〜14F に見えていたコタロに順番に対応します（GUEST の予測の技と HOST の技の開始のずれは入力の遅れそのもので、巻き戻し量に含まれている）。複雑な rollback は不要でした。
- 結果（下の表）：判定が出た瞬間の **GUEST の画面のコタロと、HOST が参照した過去のコタロの差は平均 2〜6px**（上限に当たらない ping。200ms は上限のため 24px）。参照しない場合（HOST の今）は 36〜72px。

## 9. HIT / MISS・ダメージ・吹っ飛び・Hitstop
- すべて HOST の既存処理：13%、横 560 / 上 820 × 蓄積ダメージの倍率、向きは「コタロから離れる方向」（HOST の今の位置で決まる）、ヒットストップ 7F（攻撃側・受け側）。テストで HOST の値を確認（受け側 7F・攻撃側 7F・左上へ吹っ飛び・13%）。
- GUEST へは命中イベント（命中番号・攻撃 ID・反映後のダメージ・位置）と、ダメージ・吹っ飛び後の状態が届きます。GUEST はダメージ表示を HOST の値にし、ルミポの被弾は HOST の状態で作り直します。
- 全テスト（人工遅延 10 条件 × 6 分の自動対戦を含む）で **両画面のダメージは常に一致**、終了時の位置・速度の差は 0.05 以下。
- ヒットストップは rollback 式の同期はせず、HOST の状態（ヒットストップ中フラグ・残りフレーム）を表示に使うだけ。命中の演出は命中番号ごとに 1 回。

## 10. 効果音・エフェクトの重複防止
- 使っているのは既存のものだけ：溜め `shockCharge`（演出・音）、放電 `shockBurst`（演出）・`shockZap`（音）、命中 `shockHit`（電撃のヒット演出）・`hit` + `hitZap`（音）。新しい画像・素材はありません。
- HOST：既存の処理がそのまま鳴らす・描く（Phase 3 の「追いつき」で 1 ステップに 2 回進めた時の演出も既存の Effects へ渡すようにした）。
- GUEST：**予測用ルミポを進める間は効果音を止め**（作り直しで同じ入力を何度も適用するため）、音と演出は「表示中の技」から出します。
  表示中の技は攻撃 ID ごとに同じ action を使い続け、開始音・10F の放電音・溜め / 放電の演出を **その技につき 1 回だけ**。作り直し・状態の受信が何度あっても二重になりません。
  HOST で確定した後も同じ ID なので、開始音は鳴り直しません。コタロの技も同じ仕組みで GUEST の画面に音・演出が出ます（Phase 4 では GUEST の画面のコタロの技に音が無かった）。
- テスト：1 回の電撃で GUEST・HOST とも溜め音 1・放電音 1・溜め演出 1・放電演出 1。命中時は命中音 1・電撃音 1・電撃のヒット演出 1。相打ちでもそれぞれの技の演出が 1 回ずつ。
- Phase 4 / 5 の小さな問題もここで直りました：予測の作り直しで、GUEST のぽよんの開始音が ping によっては 2〜3 回鳴ることがあった。

## 11. ぽよんとの連続入力
- 既存の規則のまま（オンライン専用のキャンセルは無し）：技の途中で別の技は出ない。技が終わる前 0.1 秒以内に押した技は先行入力で、終わった次のフレームから出る。
- テスト（HOST の毎ステップの技を記録）：ぽよん 5F 目の K → 出ない / ぽよん 15F 目の K → ぽよんが終わってから電撃 / 電撃 18F 目の J → 出ない / 電撃 33F 目の J → 電撃が終わってから。**技 → 技の途中切り替えは 0 回**。GUEST の予測も同じ結果。
- 再使用待ち：電撃が終わった直後（0.7 秒以内）の K は HOST も予測も出さない（3 回押して 1 回だけ）。

## 12. 相打ち
- 既存の `Combat.resolve()`（全員の当たりを集めてからまとめて適用）のまま。オンライン専用の相打ちルールはありません。
- テスト（押す時刻を 6ms ずつずらして同じステップの相打ちを作る）：**電撃 × 電撃・GUEST ぽよん × HOST 電撃・GUEST 電撃 × HOST ぽよん** の 3 通りとも、両方に命中・両画面のダメージ一致・位置が一致して収束・それぞれの技のヒット演出が 1 回ずつ。
- 直した点：相打ちでは攻撃側（ルミポ）が同じステップで先に被弾して技が消えるため、命中イベントの攻撃 ID が 0（＝ぽよん扱い）になり、GUEST で電撃のヒット演出が出ないことがあった → 記録しておいた技の ID を使うようにした。診断の「今の位置なら」の判定も同じ理由で修正。

## 13. 被弾時の予測
- Phase 4 / 5 と同じ：GUEST のルミポが被弾したら、HOST の被弾状態（位置・速度・被弾硬直・ダメージ）を予測より優先し、未確認の入力を適用し直します。差は 30ms で吸収（300 以上なら即座に合わせる）。
- HOST の電撃でルミポが吹っ飛ぶテスト：snap 0、左右の往復 0〜2 回以下（揺れなし）、着地後の位置・速度は HOST と完全一致。人工遅延テスト全体でも **被弾の補正の snap 0 回**（補正量の最大は ping 200ms で 178）。

### ping 200ms で分かった限界
- GUEST が K を押した時、HOST では既にルミポが被弾していた場合、それが GUEST に分かる前（約 250ms）に予測の電撃が 10F（150ms）に達し、**放電の演出と放電音だけが GUEST の画面に出てしまう**ことがあります（このテストで 5 回中 1〜2 回）。
  HOST では技が出ていないので命中・ダメージは起きず、直後に被弾の表示に変わります。rollback を使わない予測の限界として、Phase 6 ではこのままにしています。ping 100ms 以下のテストでは 0 回。
- 上限 200ms では 200ms の回線の遅れを補いきれず、逃げる相手には外れやすい（見た目HIT → MISS 18%）。

## 15. 診断表示（スクリーンショット 1 枚で両方の技が分かる）
「診断」を開くと、技ごとの表が出ます。
- HOST：PING／GUEST 入力（Hz・番号・未適用）／**LagComp ON/OFF・上限・巻き戻し 平均/中央値/最大・上限到達・invalid 参照**／
  ルミポの技ごとに「**入力 / 発動 / 拒否 / HIT / MISS** │ 押下→HOST 開始 │ 今も過去も/過去だけ/今だけ/MISS │ 補償だけで HIT（距離 60 超）」／技ごとの巻き戻し量・今と過去の差／コタロの技ごとの発動・HIT・MISS。
- GUEST：PING／予測 ON/OFF・予測誤差・snap・被弾補正／自分の技ごとに「**入力 / 予測開始 / HOST 発動 / HOST 拒否 / HIT / MISS** │ 見た目×HOST（HH/HM/MH/MM と 見た目HIT→MISS の割合）│ 今の位置ならの同じ 4 分類」／
  技ごとの「**押す→予測開始 / 押す→HOST 発動の確認 / HOST HIT→表示**」の時間と、判定の瞬間の位置の差。
- HOST の画面では、診断を開いている時だけ、遅延補償で当たった瞬間の今のコタロ（水色）・参照した過去のコタロ（黄色の点線）・電撃の判定（赤）を重ねて表示（Phase 5 の表示。最初のフレームで当たった時も出るようにした）。
- 遅延補償の切替：HOST の「LagComp」ボタン / C キー / URL `?lagcomp=off`。上限の変更（実験用）：`?lagmax=0〜300`。通常は ON・200ms。

## 17. スマホ
- GUEST のパッドに「必殺」ボタン（攻撃ボタンの上）を追加。LEFT / RIGHT・JUMP・攻撃・必殺は互いに重ならず、画面内に収まる（iPhone 13 横向き相当で確認）。

## 19. テスト結果（ローカル）
- Phase 6 の機能テスト 38/38（ping 30・60・100ms・揺れありで全項目合格）。ping 200ms は 36/38：上の「限界」の 2 項目（拒否された電撃の放電表示・上限 200ms で届かない逃げる相手）だけが想定どおり不合格（相打ち 3 通り・ダメージ一致・収束などは合格）。
- Phase 6 スマホ 9/9。
- Phase 1〜5 の回帰：接続 38/38・操作 38/38・予測 19/19・攻撃 20/20・遅延補償 12/12・スマホ（操作 10/10・攻撃 5/5・画面 8/8）・落下 / 予測中の落下 / 突然の切断 すべて合格。
- CPU 対戦（固定乱数）：EASY / NORMAL / HARD / CHALLENGE とも Version 1.0 と **完全一致**。オンライン実験（ぽよん・クラゲ電撃を両者が使用）の後に CPU 対戦をしても完全一致。試合の流れ（KO → 結果 → 再戦 → タイトル）も v1.0 と同じ。
- テストに使った疑似回線（`mock-peer.js`）で、同じ時刻に送ったメッセージの順番が入れ替わることがあったので修正しました（実際の WebRTC の reliable / ordered では起きない）。あわせて GUEST の命中イベントの重複判定を「番号の集合」にして、届く順番に頼らないようにしました。
