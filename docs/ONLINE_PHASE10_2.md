# コタロの大格闘 Online — Online Phase 10.2 調査報告（低 Ping でも GUEST の攻撃だけ HIT が約 40ms 遅れる件）

実機（PING 平均 6ms・fps 60）で GUEST の「見た目の接触→HIT」が約 40ms だった件を調べた。原因は **HOST の入力キューに残る 1〜2 件の滞留**
（通信の揺れの後に残り、通常の解消条件では消えない）で、GUEST の攻撃の開始が HOST で毎回 1〜2 ステップ遅れていた。
攻撃・必殺・泡の押下の時だけ、その手前の入力を同じステップで先に適用するようにして、滞留ぶんを削った。HOST authoritative・予測・70ms 補間・
遅延補償（上限 200ms）・技の性能・試合の流れは変更していない。

## 1. 診断値の意味（実機の値の読み方）
| 表示 | 定義（コード） | 実機の値 |
|---|---|---|
| 押す→発動確認 | GUEST が入力をサンプルした時刻 → 「HOST でその攻撃（同じ攻撃 ID）が始まった」と書かれた状態 `st` を GUEST が受け取るまで（`acceptRtt`）。= 片道 + HOST の入力キュー + 状態の送信待ち（30Hz：0〜33ms）+ 片道 | 59ms |
| 118ms（同じ行の括弧内） | 遅延補償の **巻き戻し量**（HOST が GUEST の攻撃の判定でコタロを何 ms 前の位置にしたか。HOST から `ma` で届く値の平均）。待ち時間ではない。≒ 補間 70 + 表示中の状態の古さ + 片道 + HOST の入力キュー | 118ms |
| 入力→HOSTで反映→受信 | 入力 → それを適用済みと書かれた状態を受け取るまで（各状態で最新の入力だけ測るので短めに出る） | 37ms |
| 見た目の接触→HIT | 自分の画面で技がコタロに触れて見えた時刻 → HIT の命中イベントを受け取るまで | 40ms |

3 つの値（37 / 59 / 118）はどれも「HOST で入力が適用されるまでの待ちが 約 25〜30ms」と読める（RTT 6ms なら 60Hz の位相差だけで平均 約 8ms のはず）。
今回、118ms の表示に「巻き戻し」と付け、HOST の診断に「押下の待ち（受信→適用）」を追加した。

## 3. 時間軸の比較（ぽよん・静止・揺れあり・変更前・押下からの ms・中央値）
| | GUEST（予測） | HOST（正式） |
|---|---|---|
| 入力 | 0 | 受信 18（片道）→ **適用 35〜36（キューで 17ms 待つ）** |
| 技の開始 | 5（押した次のステップ） | 36 |
| 判定が出る（4F 目） | 53 | 86〜87 |
| 見た目の接触 / 判定 | 53（GUEST の画面） | 86〜87（HOST の判定 = HIT） |
| HIT の表示 | 命中イベント受信 100 → 火花 104 | 88（HOST の画面） |

- **GUEST の画面で触れた瞬間（GUEST は 4F 目＝判定開始）、HOST の技はまだ 1〜2F 目（startup）**。HOST が同じ 4F 目に来るのは「片道 + キューの待ち」だけ後。
- 接触→HIT 47ms の内訳：片道 13（テストの中継込み。実機は 約 3）＋ **キューの待ち 17** ＋ 60Hz の位相差の一部 ＋ 命中イベントの片道 13。
  実機（片道 約 3ms）に当てはめると 3 + 約 25〜30 + 3 + 数 ms ≒ 40ms。
- HOST の攻撃は入力・技・判定・表示がすべて HOST の同じ時間軸なので、見た目の接触→反応は 0〜4ms（このため HOST 側では遅延を感じない）。

## 4. 原因：HOST の入力キューの滞留
- HOST は GUEST の入力を 1 ステップに 1 件ずつ適用する（Phase 3。予測と同じ順番にするため）。入力が届いていないステップは前の入力を続け（「続けた」）、その分だけ HOST は GUEST の入力列から 1 件遅れる。
- 到着と消費はどちらも毎秒 60 件なので、一度遅れた分（滞留）は自然には減らない。解消は「未適用 3 件超」か「2 件以上が 0.5 秒続いた」時だけで、揺れで 1 件の瞬間があるとリセットされるため、
  **1〜2 件の滞留（17〜33ms）が残り続ける**。これは揺れを吸収するための仕組み（ジッタバッファ）として働いている面もある。
- 70ms 補間：静止したコタロでは接触→HIT に影響しない（命中イベントの到着時刻は補間と無関係）。コタロが動いている時は「見た目の接触の瞬間」を前後させるが、HIT / MISS は遅延補償が GUEST の見た位置で判定する。補間は巻き戻し量 118ms の最大の部分。
- 遅延補償：コタロの位置を GUEST が見ていた位置（巻き戻し 116〜132ms、上限 200ms に未到達）に戻して判定しているので、HIT / MISS は GUEST の見た目と一致している（全試行で一致）。
  ただし判定の「時刻」を早めるものではないので、接触→HIT の待ちは補償では縮まない。

## 5. 変更：攻撃系の押下の時だけ滞留を先に適用する（`online-move.js` の `RemoteInputController.poll`）
- 攻撃・必殺・泡の押下がキューの 2〜4 番目で待っている時、その手前の入力（最大 3 件）を同じステップで既存の追いつきと同じ方法（既存の物理で 1 回ずつ）で先に適用し、押下をそのステップで適用する。
- 条件：対戦中・ルミポが場にいる・技中でない・被弾硬直とヒットストップ中でない・攻撃の先行入力が残っていない（攻撃判定やヒットストップのフレームを飛ばさない）。
- 適用する入力も順番も同じなので、予測（GUEST）と HOST の結果はずれない。移動用の揺れの吸収（キュー全体・既存の追いつき）はそのまま。
- 先に適用した後は滞留が無くなるので、次に揺れた時に「続けた」が起こりやすい（地上の技中は左右の入力を使わないので位置への影響は小さい）。
- 移動中・ジャンプの押下・ガードの押しっぱなしでは行わない。

## 6. 変更前 / 変更後（揺れあり、同じ条件・中央値）
| | 変更前 | 変更後 |
|---|---|---|
| ぽよん（静止）見た目の接触→HIT（診断値） | 約 47ms（32〜64） | **約 30ms（23〜46）** |
| ぽよん（走りながら）見た目の接触→HIT | 44ms | **30ms**（200ms の詰まりと重なった 1 回は 147ms） |
| クラゲ電撃 見た目の接触→HIT | 44ms | **26ms**（詰まりと重なった 1 回 229ms） |
| ぽよん（HOST ガード）接触→GUARD | 43ms | **27ms**（詰まりと重なった 1 回 206ms） |
| HOST の押下の待ち（受信→適用） | 17ms | **4ms** |
| 押下 → HOST の技の開始 | 36〜40ms | 21〜27ms |
| 押す→発動確認 | 50ms | 44ms |
| 巻き戻し | 132ms | 120ms |
| 揺れなし（押下の前に滞留が無い） | 先に適用 0 回・変化なし（約 27ms） | 同じ |

実機（片道 約 3ms）では、滞留の分（約 17〜30ms）が減って **見た目の接触→HIT は 約 15〜25ms** になる見込み（残りは片道 × 2・60Hz の位相差・描画）。

## 8. 変更しなかったこと
- 入力キュー全体の大きさ・既存の追いつきの条件（移動の揺れの吸収と予測の安定のため）。70ms 補間・遅延補償の上限・ガード / 泡の遅延補償なし。
- 仮の命中フィードバック（今回の主な原因が削れる滞留だったため、検討の段階まで進めていない）。
- 泡（Phase 7 の表示の時間軸）と、泡の消滅イベントの受信検証の件（今回の 40ms とは無関係）。
- 技・移動・ストック・試合の流れ・接続方式・CPU 対戦・Phase 11 の UI。

## 9. 実機で次に確認すること
1. GUEST の「見た目の接触→HIT」（ぽよん・電撃）：40ms → 約 15〜25ms になっているか。
2. HOST の「押下の待ち（受信→適用）」：中央値が 0〜10ms 程度か（大きければ押下の前に技中・先行入力などで先に適用できなかった）。「追いつき（押下 n回）」の回数。
3. GUEST の「予測誤差」「補正」「snap」「HIT→MISS」が変更前と同じ程度か。
4. 走りながら攻撃した時、HOST の画面でルミポが不自然に飛んで見えないか。
5. PING が跳ねた直後（max 200ms 級）の攻撃は今回の変更でも遅れる（詰まりの間は入力そのものが届かない）。

## 10. 残る遅れの区別（GUEST の攻撃・見た目の接触→HIT）
| 部分 | 目安（実機 RTT 6ms） | 区別 |
|---|---|---|
| 入力が HOST へ・命中イベントが GUEST へ（片道 × 2） | 約 6ms | ネットワーク（HOST authoritative では必要） |
| 60Hz のステップの位相差（入力が届いてから次の HOST のステップまで） | 0〜17ms（平均 8） | 固定ステップの構造上必要 |
| 入力キューの滞留 | 17〜33ms → 押下の時はほぼ 0 | **今回削った**（移動の揺れの吸収としては残る） |
| 受信 → 描画 | 0〜17ms | 描画のフレーム（必要） |
| PING が跳ねた時 | 詰まりの長さ | ネットワーク（削れない） |
| コタロの被弾の姿勢・吹っ飛び（火花の後） | +約 70ms | 70ms 補間（変更しない。白く光る・火花・音は命中イベントで即座） |
